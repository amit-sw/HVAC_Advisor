What This App Does

You ask an HVAC question. The app gives you three answers of increasing quality. Here's why that matters.

An HVAC Expert You Can Ask Anything

Imagine you're choosing a rooftop air conditioning unit for a building in Phoenix, Arizona. You could spend hours reading product manuals — or you could type a question in plain English and get an expert-level answer backed by real documentation.

That's what this app does. It's built as a Google Colab notebook that connects to OpenAI's AI models and a library of HVAC product documents.

💬

Ask in Plain English

Type any HVAC question — product comparisons, maintenance advice, model recommendations.

🌍

Location-Aware

Mention a city and the app automatically looks up climate data to tailor its advice.

📚

Document-Backed

Answers cite real HVAC product manuals, not guesses — so you can verify every claim.

Three Answers, Three Levels of Smarts

The app doesn't just give you one answer — it shows you three, side by side, so you can see the difference between a basic AI guess and a deeply grounded recommendation. Think of it like asking three different consultants:

1
Baseline LLM — The Generalist

Asks the AI directly with no reference material. Like asking a smart friend who hasn't read the manuals — they'll give a reasonable answer, but might make things up.

2
RAG — The Researcher

First searches HVAC product documents, then feeds the relevant snippets to the AI. Like a consultant who reads the manuals before answering — grounded, with citations.

3
Deep Agent — The Senior Expert

An autonomous agent that decides what to do: checks if the question mentions a location, looks up climate data, searches documents, and synthesizes everything. Like a senior engineer who knows what questions to ask before answering yours.

Under the Hood: Config Manager

Everything starts with credentials. Here's how the app loads its settings — notice the fallback pattern that checks multiple sources:

CODE 
def get_secret(name: str, default: str = "") -> str:
    if os.getenv(name):
        return os.getenv(name)
    if userdata is not None:
        try:
            value = userdata.get(name)
            if value:
                return value
        except Exception:
            pass
    return default
PLAIN ENGLISH

Define a helper that looks up a secret value by name.

First, check if it's set as an environment variable on the computer.

If found there, use it immediately.

If not, check if we're running in Google Colab...

...and try to read from Colab's built-in secrets manager.

Look up the secret by name in Colab.

If we got a value, use it.

Return the Colab value.

If anything goes wrong with Colab secrets, just move on.

Silently skip — no crash, just try the next option.

If nothing worked, return a default value (usually empty).

💡
Defensive Fallbacks

This "try here, then there, then give up gracefully" pattern is everywhere in professional code. It's called a fallback chain. When you're directing an AI to write code that loads configuration, asking for fallback behavior makes it much more robust.

How the Pieces Talk

Data flows through this app like packages through a sorting facility. Let's trace the full journey from question to answer.

Three Pipelines, One App

Each answer mode has its own pipeline — a different path the data takes from your question to the final answer. The simplest mode is a straight line; the most complex is a branching decision tree.

➡

Baseline: Straight Line

Query goes in, answer comes out. One hop: your question straight to the LLM. No documents, no climate data.

🔄

RAG: Two-Step

First search documents, then ask the LLM with the evidence attached. Two hops: vector store, then LLM.

🌳

Deep Agent: Decision Tree

The agent reads the query, decides whether to call climate first, then searches docs, then synthesizes. It chooses its own path.

Inside the RAG Pipeline

The RAG mode is the heart of this app — it's the pattern that makes AI answers trustworthy. Here's the actual code that runs it:

CODE 
def run_rag(query: str, top_k: int):
    add_trace("RAG mode started")
    retrieval = search_hvac_docs(query, top_k=top_k)
    if retrieval["results"]:
        response = rag_llm.invoke(
            rag_prompt.format_messages(
                query=query,
                evidence_text=retrieval["evidence_text"]
        ))
        answer = message_to_text(response)
    else:
        answer = "I could not ground an answer..."
    return {"answer": answer, ...}

Log a breadcrumb so we can trace what happened later.

If we found any matching documents...

...send the question AND the evidence to the AI model together...

...using a pre-built template that tells the AI to only answer from the evidence...

...passing in the original question...

...and the actual document text we retrieved.

Wait for the AI to respond and extract the text.

Convert the AI's response into plain text.

But if no documents were found...

...honestly say the answer can't be grounded. No guessing!

Package everything up and return it.

The Outside World

This app doesn't work alone — it reaches out to four external services. Understanding them helps you debug failures and control costs.

Four Services, Four Lifelines

Think of the app as a detective agency. It has smart analysts inside, but it depends on outside informants for data. If any informant goes silent, the case stalls. Here are the four external services this app calls:

📍

Open-Meteo Geocoder

Converts a city name like "Phoenix, Arizona" into GPS coordinates (lat/lon). Free, no API key needed.

🌍

Nominatim (Backup)

OpenStreetMap's geocoder — a second opinion if Open-Meteo can't find the location. Also free.

🌡

Open-Meteo Climate Archive

Returns 10 years of daily temperature and precipitation data for any GPS coordinate. Free, no key.

🔑

OpenAI (Vector Store + LLM)

Two services in one: the vector store searches HVAC documents, and the LLM generates answers. Requires an API key and costs money per request.

How Location Lookup Works

Converting "Phoenix Arizona" into GPS coordinates sounds simple, but humans type locations in messy ways. The app tries multiple variations of the input to maximize its chances:

CODE 
def geocode_location(location: str):
    attempted = []
    for candidate in candidate_location_queries(location):
        attempted.append(candidate)
        geo = http_get_json(
            "https://geocoding-api.open-meteo.com/v1/search",
            {"name": candidate, "count": 3},
        )
        matches = geo.get("results") or []
        if matches:
            return matches[0], attempted
    # If Open-Meteo fails, try Nominatim...
PLAIN ENGLISH

Define a function that turns a city name into coordinates.

Keep a list of everything we tried (for debugging later).

Generate several ways to spell/format the location and try each one.

Record each attempt in our tried-list.

Call the Open-Meteo geocoding API...

...with the search endpoint...

...asking for up to 3 matches.

 

Pull out the results (or an empty list if none).

If we got at least one match...

...return the best one plus our attempt log. Done!

If Open-Meteo struck out on all variants, fall back to Nominatim.

From Raw Weather to HVAC Advice

Once we have GPS coordinates, the app pulls 10 years of daily weather data and boils it down to HVAC-relevant insights. Here's the transformation pipeline:

1
Fetch 10 Years of Daily Data

Calls Open-Meteo's archive API for daily high temperatures, low temperatures, and precipitation from the last decade.

2
Build a Monthly Summary

Groups all 3,650+ days by month and calculates averages. This smooths out weird weather days and reveals the true climate pattern.

3
Extract Key Metrics

Finds the hottest month's average high, the coldest month's average low, annual precipitation, and typical daily temperature range — all converted to Fahrenheit and inches.

4
Generate HVAC Notes

Rules-based logic translates weather numbers into maintenance advice. Example: "Hottest month above 90F" triggers "Prioritize condenser coil cleaning before summer."

💡
Data Pipelines Are Everywhere

This fetch-transform-summarize pattern is called a data pipeline. Almost every AI application has one. Raw data from an external API is rarely useful on its own — it needs to be cleaned, aggregated, and translated into something your application can use. When directing AI tools to build data features, always think: what's the raw input, what transformations are needed, and what's the useful output?

The Clever Tricks

The difference between a prototype and production code is the small details. Here are the engineering patterns that make this app robust.

The Location Guessing Game

Humans type locations in chaotic ways: "phoenix az", "Phoenix, Arizona", "phoenix arizona usa". The app handles this with a clever variant generator — like a post office clerk who tries different interpretations of a badly-written address:

CODE 
def candidate_location_queries(location):
    cleaned = " ".join(location.replace(",", " ").split())
    variants = []
    add_variant(location.strip())
    add_variant(cleaned)
    tokens = cleaned.split()
    if len(tokens) >= 2:
        for tail_size in (3, 2, 1):
            state_part = " ".join(tokens[-tail_size:])
            if state_part.lower() in US_STATE_NAMES:
                add_variant(f"{city_part}, {state_part}")
                break
PLAIN ENGLISH

Generate multiple ways to search for a location.

First, normalize: remove commas, collapse extra spaces.

Start collecting different formatted versions.

Try the exact input as-is (maybe it already works).

Try the cleaned-up version too.

Split into individual words to analyze the structure.

If there are at least 2 words (likely city + state)...

...check if the last 3, 2, or 1 words are a US state name...

...by looking at the end of the input...

...and comparing against all 50 state names.

If it matches, format as "City, State" with a comma.

Stop checking once we find a state match.

💡
Input Normalization

This technique is called input normalization. Users will always surprise you with how they format things. Instead of demanding perfect input, good code adapts. When telling AI to build user-facing features, always specify: "handle messy input gracefully."

Turning Weather into Maintenance Advice

Raw temperature numbers are useless to an HVAC decision-maker. The app uses rules-based logic to translate climate data into actionable maintenance notes — like a doctor translating blood test numbers into health recommendations:

CODE 
def build_maintenance_notes(hottest_month_avg_high_f,
        coldest_month_avg_low_f, annual_precip_in):
    notes = []
    if hottest_month_avg_high_f >= 90:
        notes.append("Prioritize condenser coil
            cleaning and refrigerant charge
            verification before summer.")
    if coldest_month_avg_low_f <= 32:
        notes.append("Include freeze-stat checks
            and drain-pan protection
            before winter.")
    if annual_precip_in <= 15:
        notes.append("Check filters for dust
            accumulation in dry conditions.")
PLAIN ENGLISH

Given climate stats, generate maintenance recommendations.

 

Start with an empty list of recommendations.

If the hottest month averages 90F or above...

...recommend pre-summer maintenance:

clean cooling coils and check refrigerant levels

to handle peak cooling demand.

If the coldest month dips to freezing or below...

...recommend winter prep:

Deduplication & Trace Logging

The Deep Agent might search documents multiple times with different queries. Without deduplication, you'd see the same document chunk repeated in the results. Here's how the app prevents that — like a librarian removing duplicate copies before handing you a reading list:

CODE 
unique_evidence = []
seen = set()
for item in tool_evidence:
    key = (item.get("file_id"),
           item.get("snippet"))
    if key in seen:
        continue
    seen.add(key)
    unique_evidence.append(item)
PLAIN ENGLISH

Start a clean list for unique results only.

Create a "seen before" checklist (a set — very fast to search).

Go through every document chunk the agent found...

...create a fingerprint from the file ID...

...and the text snippet (same file + same text = duplicate).

If we've already seen this exact fingerprint...

...skip it. Don't add it again.

Otherwise, mark it as seen...

...and add it to our clean list.

Meanwhile, every major action gets logged to a trace — a timeline of what happened and when. This is invaluable for debugging:

CODE 
TRACE_LOG = []

def add_trace(message: str) -> None:
    timestamp = datetime.now().strftime("%H:%M:%S")
    TRACE_LOG.append(f"{timestamp} | {message}")
PLAIN ENGLISH

Create a global list to track everything that happens.

 

Define a helper to add an entry to the log.

Stamp each entry with the current time (hours:minutes:seconds).

Add the timestamped message to the log list.

💡
Observability Is a Superpower

Observability — the ability to see what your app is doing — separates debuggable systems from mysterious ones. When directing AI to build features, always ask: "add logging at each major step." Future-you will thank present-you when something breaks at 2 AM.
